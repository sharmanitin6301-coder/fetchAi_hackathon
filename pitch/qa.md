# AccessFix — Judge Q&A Preparation

Curated responses to the most challenging, likely technical and design questions from judges.

---

### Q1: "Isn't this just axe plus ChatGPT?"

**Short Answer:**  
No. Axe checks static syntax rules; ChatGPT guesses code. AccessFix is a **closed-loop verification system** that tests real task completion.

**Detailed Points:**
- **Task Verification vs. Rule Checking:** Axe can tell you an image lacks an `alt` attribute, but it cannot tell you whether a blind user can actually buy a product or sign up for a newsletter. Our Blind Agent actively navigates using only keyboard events (`Tab`, `Enter`, `Type`) and accessibility snapshots to test task completion.
- **Closed-Loop Feedback:** A raw LLM hallucinating code often breaks page structure or introduces new bugs. AccessFix applies fixes to an isolated working copy, measures layout shifts, re-runs Axe, and re-runs the Blind Agent. If the agent is still stuck, the verifier automatically loops back with the stuck step to retry (up to 3 rounds).
- **Deterministic Math Where It Counts:** Contrast fixes and focus rings are not generated by an LLM; they are calculated with deterministic relative luminance stepping to guarantee WCAG 4.5:1 compliance.

### Q2: "Can it break my site or change my visual design?"

**Short Answer:**  
No. We use isolated working copies, non-destructive Cheerio patches, and an automated pixel-level layout shift detector.

**Detailed Points:**
- **Zero Direct Mutation:** AccessFix never modifies production files or source repositories directly. It outputs an industry-standard unified `.diff` file that developers review and commit via `git apply`.
- **Bounding-Box Layout Shift Checks:** Playwright measures the bounding box (`x`, `y`, `width`, `height`) of all key elements before and after patching. Any visual movement greater than 5 CSS pixels is immediately flagged with a `[REVIEW]` status and routed to human review.
- **Conservative Attribute Preservation:** When converting non-semantic elements (e.g., `<div class="btn-subscribe" onclick="...">` to `<button type="button">`), all existing CSS classes, IDs, dataset attributes, and styles are preserved intact so styling does not break.

### Q3: "Does it replace human accessibility auditors?"

**Short Answer:**  
Never. We explicitly state: *"Automation cannot catch everything. A human review is still needed."*

**Detailed Points:**
- **Eliminating the 80% Mechanical Toil:** Developers waste weeks manually creating labels, calculating contrast hex codes, inserting landmarks, and fixing button tags. AccessFix automates these routine, well-defined barriers.
- **Needs-a-Human Triage Queue:** Subjective issues—such as brand-sensitive focus indicator colors, rich widget interactions, or visual movements—are routed directly to the "Needs a Human" tab with an explicit explanation of why human judgment is required.
- **Empowering Auditors:** Instead of handing developers a 50-page PDF report of errors, auditors can hand them a ready-to-test code diff, reserving their billable hours for nuanced user testing.

### Q4: "What's next for AccessFix?"

**Short Answer:**  
CI/CD pull request gating, a real-time browser extension polyfill, and multi-step flow verification.

**Detailed Points:**
- **Phase 1 — GitHub Action / CI Bot:** Prevent accessibility regressions before they merge. If a PR introduces an unreachable interactive control or breaks a keyboard task, CI fails with an attached `.diff` repair patch.
- **Phase 2 — Assistive Browser Extension:** A client-side extension that injects verified semantic patches into live websites in real time, repairing inaccessible forms for blind users on the fly.
- **Phase 3 — Multi-Page Workflows:** Extend task discovery and blind agent navigation across multi-page e-commerce checkouts, authentication modals, and dynamic Single-Page Applications (SPAs).

### Q5: "Why a keyboard-only agent? Why not allow mouse clicks?"

**Short Answer:**  
Because blind and motor-disabled visitors cannot use a mouse. A mouse-clicking agent tests sighted convenience, not accessibility.

**Detailed Points:**
- **True Assistive Tech Simulation:** Screen-reader users (using NVDA, JAWS, VoiceOver) and users with physical motor disabilities navigate exclusively through keyboard commands (`Tab`, `Shift+Tab`, `Arrow` keys, `Enter`, `Space`).
- **Exposing Real Traps:** A standard web agent using coordinates or DOM `element.click()` would have successfully clicked the unlabelled `<div>` on our broken demo site and reported success! Only a strict keyboard-only agent gets trapped, correctly identifying that the element lacks a `tabindex`, keyboard event listeners, and an accessible role.
- **Aria Snapshot Only:** The agent observes only what a screen reader announces (`{ role, name }` and trimmed aria snapshots)—no DOM tree peeking.

### Q6: "What if the LLM makes a mistake or hallucinates?"

**Short Answer:**  
The pipeline does not trust the LLM; the Verifier tests the actual browser outcome.

**Detailed Points:**
- **Axe Verification:** If an LLM-generated alt text or label is malformed, Axe immediately flags it during the verification pass.
- **Agent Behavioral Verification:** If the LLM generates a fix that doesn't actually make the button reachable or activatable, the Blind Agent will fail again upon re-test.
- **Max 3 Retries & Escalation:** If after 3 rounds the agent is still failing, AccessFix stops, rejects the faulty op, and safely escalates the problem to the "Needs a Human" queue rather than applying an unverified change.
- **Deterministic Guardrails:** High-risk fixes (contrast ratios, HTML lang, focus visibility CSS) bypass the LLM entirely, executing through verified deterministic TypeScript/JavaScript logic.
